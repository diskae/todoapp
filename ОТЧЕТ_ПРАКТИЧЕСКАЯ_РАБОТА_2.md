### Шаг 2. Разработка бизнес-логики и CLI приложения (Ветка `feat/todo-app-implementation`)

В соответствии с моделью **GitHub Flow** от ветки `main` создана тематическая ветка:
```bash
git checkout -b feat/todo-app-implementation
```

#### 1. Класс бизнес-логики `TodoList.java`
Создан класс `src/main/java/org/example/TodoList.java`, инкапсулирующий коллекцию задач и методы для работы с ней:
* `add(String item)` — добавление непустой строки задачи с удалением начальных/конечных пробелов;
* `remove(int index)` — удаление задачи по индексу с валидацией границ;
* `getAll()` — получение защитной копии списка задач;
* `size()` — получение текущего количества задач.

*Коммит:* `git commit -m "add TodoList"`

#### 2. Консольный интерфейс `TodoApp.java`
Создан класс `src/main/java/org/example/TodoApp.java`, реализующий цикл обработки пользовательского ввода (CLI) со стандартным потоком ввода/вывода:
* Поддержка команд: `add <task>`, `remove <index>`, `list`, `exit`;
* Обработка некорректных аргументов и ошибок формата (`NumberFormatException`).

*Коммит:* `git commit -m "add TodoApp"`

#### 3. Модульное тестирование `TodoListTest.java`
Создан тестовый класс `src/test/java/org/example/TodoListTest.java` с использованием **JUnit 5 Jupiter**:
* `addAndList()` — проверка добавления элемента, тримминга пробелов и размера;
* `remove()` — проверка успешного удаления и граничных условий (несуществующий индекс);
* `addEmptyIgnored()` — проверка игнорирования пустых строк, пробелов и `null`.

*Коммит:* `git commit -m "add tests for the todo app"`

#### 4. Слияние изменений (Pull Request #1)
Все тесты успешно пройдены локально (`./gradlew test`). Изменения влиты в `main` через Pull Request:
```bash

git merge --no-ff feat/todo-app-implementation -m "Merge pull request #1 from feat/todo-app-implementation"
```

### Шаг 3. Настройка сборки Fat-JAR и CI-пайплайна (Ветка `feat/actions`)

Создана новая функциональная ветка:
```bash
git checkout -b feat/actions
```

#### 1. Управление версионированием проекта
Создан файл `gradle.properties`:
```properties
# Version used by build and by CI to tag the release
version=0.1.0
```

#### 2. Настройка `build.gradle` для сборки Fat-JAR
Подключен плагин `com.github.johnrengelman.shadow` версии `8.1.1`:
* Настроена задача `shadowJar` (базовое имя `todo-app`, пустой классификатор, объединение служебных файлов);
* Отключена генерация тонкого JAR (`tasks.jar { enabled = false }`);
* Задача `tasks.build` перенастроена в зависимость от `shadowJar`, что гарантирует получение готового самодостаточного исполняемого архива `todo-app-0.1.0.jar`.

*Коммит:* `git commit -m "change build.gradle for jar build"`

#### 3. Конфигурация CI / Build & Release (`.github/workflows/ci.yml`)
Создан сценарий GitHub Actions, запускающийся на каждый `push` в ветку `main` и `pull_request`:
* **Шаги пайплайна:**
  1. `actions/checkout@v4` — загрузка репозитория;
  2. `chmod +x gradlew` — установка прав исполнения;
  3. `actions/setup-java@v4` — развертывание JDK 21 (Temurin);
  4. `actions/cache@v4` — кеширование зависимостей Gradle для ускорения сборок;
  5. Извлечение версии проекта из `gradle.properties` в переменную шага;
  6. `./gradlew --no-daemon clean build` — выполнение компиляции, модульных тестов и сборки fat-JAR. **Если тесты падают, весь пайплайн аварийно завершается, предотвращая дефектный релиз!**;
  7. Создание релиза в **GitHub Releases** с тегом `v<version>` и прикреплением исполняемого файла `todo-app-<version>.jar`.

*Коммит:* `git commit -m "add ci"`

#### 4. Слияние изменений (Pull Request #2)
```bash
git checkout main
git merge --no-ff feat/actions -m "Merge pull request #2 from feat/actions"
```

### Шаг 5. Выполнение дополнительного задания (стр. 52 методических указаний)

Для реализации повышенного уровня сложности создана ветка:
```bash
git checkout -b feat/app-extensions-and-nightly
```

#### 1. Новые команды приложения
В `TodoList.java` и `TodoApp.java` добавлены функции:
1. **`clear`** — полная очистка списка задач (`list.clear()`);
2. **`done <index>`** — отметка задачи как выполненной с добавлением префикса `[DONE] ` и защитой от дублирования отметки;
3. **`search <текст>`** — поиск задач по подстроке без учета регистра букв.

#### 2. Расширение набора модульных тестов JUnit 5
В `TodoListTest.java` добавлены специализированные тест-кейсы:
* `clear()` — проверка полного сброса списка;
* `markDone()` — проверка добавления префикса `[DONE] ` и идемпотентности;
* `markDoneInvalidIndex()` — проверка граничных значений при попытке отметки несуществующей задачи;
* `search()` — проверка поиска по регистронезависимой подстроке;
* `searchEmptyQuery()` — проверка поведения при пустом поисковом запросе.

#### 3. Ночной пайплайн сборки (`.github/workflows/nightly.yml`)
Создан сценарий регулярной ночной сборки по расписанию (**cron**):
* **Расписание:** `cron: '0 2 * * *'` (ежедневно в 02:00 UTC) + поддержка ручного запуска `workflow_dispatch`;
* **Назначение:** проверка стабильности кодовой базы и актуальности зависимостей без создания релиза и без засорения реестра пакетов.

## 7.5 Краткий вывод по проделанной работе

В ходе выполнения практического занятия № 2 была полностью изучена и практически освоена современная методология разработки программного обеспечения с применением системы контроля версий Git и средств CI/CD:

1. **Освоена модель GitHub Flow:** разработка велась через изолированные тематические ветки с последующим слиянием через формализованные Pull Request'ы, что обеспечивает постоянную стабильность ветки `main`.
2. **Реализована архитектура приложения и автоматизированные тесты:** разработано консольное приложение на языке Java с соблюдением стандартов кодирования и строгой изоляцией бизнес-логики (`TodoList`) от интерфейса пользователя (`TodoApp`). Написан полный набор тестов на фреймворке JUnit 5.
3. **Автоматизирована непрерывная интеграция (CI):** с помощью GitHub Actions настроен пайплайн, автоматически валидирующий каждый push и PR. Пайплайн предотвращает интеграцию некорректного кода благодаря автоматическому запуску юнит-тестов перед сборкой.
4. **Реализована непрерывная доставка (CD):** при успехе сборки автоматически создается GitHub Release с готовым к распространению самодостаточным Fat-JAR (Shadow Plugin), а также осуществляется публикация артефакта в реестр GitHub Packages (Maven Repository).
5. **Внедрен ночной мониторинг стабильности:** настроен workflow по расписанию (nightly build cron), периодически проверяющий работоспособность проекта без побочных эффектов.

Все задачи и требования методических указаний (включая блок дополнительного функционала) выполнены в полном объеме.
